# Operations console read contract

**Status:** current contract of the read-only operations console (#533). Section 2 describes shipped code and the tests that pin it. Section 3 lists contracts that are **pending**; nothing in section 3 is shipped. The console introduces no policy, health, cost, session or decision logic: every value it shows is produced by a Go projection the CLI also uses, and a value no projection can produce is shown as unknown or unavailable.

Companion documents: [operations console guide](../guides/operations-console.md), [console access and pairing](console-access.md), [legacy dashboard migration map](legacy-dashboard-migration-map.md), [authentication and key scopes](authentication-and-key-scopes.md).

## 1. Principles

1. **One Go implementation per concept.** `internal/console` calls the shared projections (`fleet.Project`, `costs.Build`, `session.LoadDetail` / `LoadTimelinePage`, `evidence.Store.Detail`, `evidence.Store.ActivityBuckets`, `events.FromEvidence`, `evidence.OutcomeOf`); the CLI calls the same functions. The browser (`internal/console/frontend`) formats and lays out only.
2. **Durable facts come from the shared store, read-only; live facts come from each process's own runtime record.** The console process opens the evidence and session stores with `mode=ro` (`evidence.OpenReadOnly`, `session.OpenReadOnly`). Live process facts (liveness, version, active catalog generation, reload rejection, loaded config digests) come from the runtime record each `talon serve` writes into the data directory (§2.4); they are never inferred from the store.
3. **Unknown is a value.** Every DTO section carries `availability {state: ok|partial|empty|unavailable|unknown, source, as_of, error, note, unavailable[]}`. A failed query, a missing source or a figure that is not a measurement yields that state with the reason, never a zero and never healthy.
4. **Windows and units are explicit.** Cost and today's figures use UTC day, last 7 days and UTC calendar month (`costs.Window`). Fleet counters use the rolling windows of `fleet.DefaultThresholds` and say so (`counter_windows`). Amounts are in the active pricing table's currency; `*_eur` field names are historical. Amounts are never converted between currencies.
5. **Bounded reads.** Every list has a server maximum and a keyset cursor with documented order; search is exact or prefix and bounded; no request decodes the evidence table in full.
6. **The browser credential reaches only the console.** `/console/v1/*` is served by the console process behind the read-only browser session; the process mounts no data-plane route, and the data plane ignores the console cookie ([console access](console-access.md)).

### 2.1 Decision, dispatch and downstream (`evidence.OutcomeOf`)

Timeline rows (`records[].outcome`, also on `talon audit list --json`) and evidence detail (`detail.outcome`) carry three separate facts: `decision` (allowed | denied | approval_required, the last only for an Action Gateway operation awaiting a reviewer), `dispatch` (not_dispatched | dispatched | unknown | not_recorded), `downstream` (none | completed | rejected | failed | unknown | cache | not_recorded), plus `response_withheld`, `tool` and `basis` (the recorded fact each axis was read from). The rules use only what the writing code records:

| Record | Dispatch | Downstream | Because |
|---|---|---|---|
| `proxy_tool_blocked` | not_dispatched | none | written on the MCP proxy's pre-dispatch deny path |
| `proxy_tool_call` allowed / denied | dispatched | completed (answer withheld when denied) | forwarded and answered; a denied one failed output scanning after the answer |
| `proxy_upstream_error` with a vendor JSON-RPC error | dispatched | rejected | the upstream executed the call and returned its own error |
| `proxy_upstream_error` with status `unknown` | unknown | unknown | handed to the transport, no trustworthy answer |
| `proxy_upstream_error`, other | not_dispatched | none | failed before the transport |
| `gateway` with `cache_hit` | not_dispatched | cache | served from Talon's semantic cache; no provider call |
| `gateway` allowed, no error | dispatched | completed | forwarded and answered |
| `gateway` allowed with an error, or `gateway_failover_attempt` | dispatched only with a recorded provider HTTP status (`failover.upstream_status`), else unknown | failed / unknown | a transport error alone does not prove delivery |
| `gateway` denied | not_dispatched at stage `policy_evaluation` / `pre_execution`; dispatched with the answer withheld at `output_validation`; not_recorded otherwise | | primary explanation stage |
| `action_lifecycle` | from `result_provenance` (observed / not_dispatched / unknown) and `attempt_status`; `authorization_refused` is not_dispatched; operation status `awaiting_approval` is decision `approval_required` and not_dispatched (the signed `policy_decision.allowed` is true on that record, which only says the operation was established); operation status `denied` is not_dispatched | | action dispatcher facts |
| anything else | not_recorded | not_recorded | the record type carries no such fact |

Pinned by `TestOutcomeOf_SeparatesDecisionDispatchAndDownstream` (constructed records) and `TestOutcomeOf_RealGatewayRecords` (records the gateway writes: cache hit with the provider call counter unchanged, provider 503 before a fallback, connection failure).

### 2.2 Numbers kept for compatibility

A field listed in a report's `unavailable_fields`, a fleet row's `unavailable_fields` (`spend_day`, `spend_month` when that period's priced records are not all in the row's currency), or a partial section's `availability.unavailable` keeps its historical value only so existing scripts keep parsing. The console renders it as unavailable with its reason (`internal/console/frontend/src/lib/availability.ts`, `lib/costs.ts`, unit-tested); `talon agents` prints `n/a (currencies differ)`. Unpriced model calls are different: the cost report counts them (`unpriced_records`) and says the amounts understate spend, but fleet health does not use that count as a signal, so a use case can read healthy while some of its calls carry no price. A fleet budget period whose records are not comparable is not evaluated: the row carries the cause `budget_not_comparable` and needs attention instead of being blocked or healthy on a mixed sum (`TestProject_ForeignCurrencyIsNotComparedWithCaps`).

### 2.4 Runtime records (#538)

Each `talon serve` process publishes `<data_dir>/runtime/<instance>.json` (`internal/runtimestatus`) on start, every 5 s, and once more with `state: stopped` on graceful shutdown. Writes are atomic (temp file + rename). The record holds: instance id, roles (`mcp_proxy`, `gateway`, `native`), version and commit, pid and host, start and write time, a per-instance `sequence`, the installation fingerprint (HMAC of a fixed label under the evidence signing key; the key itself is never written), and, from the process's reloader, the active catalog generation, scan digest, activation time, reload rejection with causes and the per-agent policy digests; plus the path, sha256 and load time of `--proxy-config` / `--gateway-config`, and `agent_keys` (#533): how many use cases of the active generation declare an agent key (`agent.key.secret_name`), how many keys the process's identity registry holds, and the names of the use cases whose key it does not hold. Names and counts only: never key material or a digest of it. A process that fails during start-up (after it has its data directory and signing key) writes one `startup-failure-<roles>.json` record with `state: failed` and `startup_failure {code, reason}`: a fixed code (`agent_key_unavailable`, `no_keyed_agents`, `secrets_store`, `configuration`) and a fixed sentence chosen by the process, never the raw error, which can quote configuration. The name is deterministic, so a supervisor restarting a failing process overwrites one record; a later process serving the same roles removes it when it starts. `assess` reads a failed record as `offline` with "failed to start … ago: <reason>".

The console reads the directory read-only. `runtimestatus.Reader.Assess` derives, in Go:

| State | When |
|---|---|
| `running` | heartbeat younger than 3 heartbeats |
| `stale` | older than 3, younger than 12 heartbeats (hung, overloaded or killed) |
| `offline` | a recorded graceful shutdown, a heartbeat older than 12 beats, or a role the configuration expects that no process has reported |
| `not_configured` | a role neither expected by the console's configuration (`--proxy-config`, an enabled gateway config) nor reported |
| `unknown` | the runtime directory cannot be read, the console was started without its data directory and signing key, or the role's configuration exists but cannot be parsed (a broken gateway config is never read as `not_configured`) |

Records with another installation's fingerprint, an unknown schema, malformed JSON or over 64 KiB are listed as `rejected`, never combined. Every running instance is `current`; a role reports its most relevant instance (running before stale before offline, newest first within a state), so a newer instance that stopped never hides an older one that still serves. Instances that neither run nor represent a role stay listed as history with their own state. A record with a lower `sequence` than one already seen never replaces it. The console has no network path to the data plane, no Docker socket and no new listener; the store's sessions and evidence are read independently of runtime state.

### 2.7 Investigation presentation (#533)

The browser words what the DTOs carry; it adds no fact. `lib/outcome.ts` turns `evidence.OutcomeOf` into one sentence and claims a destination answer only when `dispatch` is `dispatched` and `downstream` says so: *Talon denied it — not dispatched*, *Talon allowed it — dispatched — destination responded / rejected it / attempt failed*, *Outcome unknown* when dispatch is unknown, and no destination claim when the record type does not record dispatch. The wording holds for every record type that maps to the canonical outcome (gateway, MCP proxy, Action Gateway lifecycle): it never names a transport hand-off or a provider HTTP status the basis does not record, and it quotes `outcome.basis`. `lib/proof.ts` sorts a record's or session's facts into Talon's facts (the identity Talon resolved, its decision, dispatch as recorded, model route, intercepted tool, recorded cost), headed by `trust`: **Talon-recorded, signature verified** for an evidence record the console checked, **Talon-recorded** for a session summary (no per-record signature check), and **Recorded claims — not reliable** when the signature fails, in which case the evidence page shows no outcome story; **Application-reported** (only values the record carries as client assertions: `orchestration.session_source` `client_asserted` / `vendor_asserted` session ids, asserted sub-agents, `request_source_id`) and **Not independently verified** (what the destination did beyond the recorded answer; actions outside the gateway and MCP proxy; business outcomes). No application-side result is fetched; a valid signature is stated to prove the record's integrity, not the surrounding workflow. Breadcrumbs (tenant scope → AI use case → session → evidence) are built from the URL and the record shown; the use-case activity range is the `range` URL parameter. With no tenant selected, the Costs page lists month-to-date spend per (tenant, use case) from the fleet rows of `use-cases` (never summed across tenants or currencies) above the single-tenant cost report. Pinned by `lib/outcome.test.ts` and `tests/browser/06-console-investigation.spec.js`.

### 2.8 Approvals (#565)

The console shows that Action Gateway approvals exist, why they are required and what happened to them. It takes no decision, has no decision route, and shows no argument value.

**One projection.** `approval` is `action.BuildApprovalView`, the projection the reviewer API and `talon approvals show` render, built here under the **operational disclosure**: `arguments[]` carry `name` only (the DTO has no value field), `bound.arguments_digest` is absent (a digest of low-entropy values is an indirect disclosure), destinations are reduced to method, scheme and host, and `decision` carries `reason_recorded` but never the reason's text. Everything else is the same fact with the same semantics: stored status, eligibility, approver groups, the bound rule id and layer, the current rule text, decision and execution outcome. The data is minimized in Go before it leaves the process, not hidden by the browser. Exact values are read by an approver of the required group with `talon approvals show <approval-id>`.

**A paired browser is not a reviewer.** The console keeps its pairing model: one read-only browser session for the installation. The `tenant` parameter is a **filter, not an authorization boundary**: a paired browser can read every tenant's approvals (without values). Reviewer authorization (tenant scope and approver groups) exists on the data plane's reviewer API only. Corporate reviewer identity, a browser review page with values and decision controls, notifications, assignment and delegation are Enterprise scope.

**Stored facts and inferences are kept apart**, in details, lists, counts, findings and use-case indicators alike:

| Statement | Source | Reads as |
|---|---|---|
| An approval is **unresolved** | the store: its status is `pending` | `unresolved: true`; `approvals.total.unresolved`; exact, independent of any configuration |
| Its lifetime elapsed | the store and the clock | `eligibility.state: expired`, `basis: lifetime`. It stays `pending` in the store: a read never closes it |
| **Potentially actionable** | the current configuration **files** compile to the policy and action definition it was established under (`effective.BuildActionConfigs`) | `class: potentially_actionable`, `basis: current_files`. Not a statement about a running process |
| **Actionable** | the same, **and** every running `talon serve` is proven to have loaded exactly those files (`runtimestatus.ProveActionPolicy`, §2.5) | `class: actionable`, `basis: runtime_confirmed` |
| Not decidable | the lifetime elapsed; or the files that **every running process is proven to have loaded** compile to another policy or definition than the one bound | `class: not_decidable`, `state: expired` (`basis: lifetime`) or `stale_policy` / `stale_definition` (`basis: runtime_confirmed`). Never inferred from files alone |
| **Unknown** | whether the deciding process would accept a decision cannot be established: the files **differ from the binding while no running process is proven to run them** (the process may still hold the configuration the request was established under); the use case is no longer in the files; the policy does not compile; the gateway config cannot be read; or the action is discovered from an MCP source (the console runs no discovery) | `class: unknown`, never `actionable`, never `not_decidable` and never dropped from the default selection. The comparison of the binding with the files is kept as its own fact: `eligibility.policy` / `eligibility.definition` = `unchanged` \| `changed` \| `unknown` |
| Decided | the store | `class: decided`, with `decision {status, decided_by, decided_group, decided_at, reason_recorded}` |

The deciding process stays the only authority: it re-checks authorization, lifetime, policy, definition and lifecycle on every decision and every claim, whatever the console showed.

**Counts.** `approvals` is `{availability, total, use_cases[], basis}`; each count is `{unresolved, eligibility {actionable, potentially_actionable, not_decidable, unknown}}`. `unresolved` is one grouped query over all rows. `eligibility` comes from a second query grouped by what eligibility depends on (use case, action, bound digests) and classified once per group, so no page bound can make a count wrong. Both queries run in **one read transaction** (`action.Reader.UnresolvedCounts`): they see one snapshot of the store, so `eligibility` sums to `unresolved` for every use case and for the total, whatever is decided while the summary is computed. When there are more distinct bindings than one request reads, `eligibility` is omitted and the section is `partial`; when the store cannot be read, `total` is omitted and the section is `unavailable`. Neither is ever reported as zero. An installation that never established an operation has **none** of the action tables: that reads `empty` with a true zero, and the console creates nothing. A store that has only some of the tables or columns a reader needs (an interrupted creation, a damaged database, a store written by another version) is **not** an unused installation: every approval section reads `unavailable` and names what is missing, no count is reported, and `approvals/{id}` answers 503, not 404 (`action.Reader.Schema`).

**An empty page is not an empty selection.** A listing page ends at the listing's scan bound, so it can hold no item while the selection continues. `page` says which it is: `empty_selection` (the first page, no item, no cursor: only this means "no approval", with availability `empty`), `continues` (a `next` cursor exists; the page may hold no item, and the note says that the selection is not exhausted), `end` (no cursor: the selection is exhausted with this page, which is empty when it was reached through a cursor). The reviewer API states the same with `next`, and `talon approvals list` words it the same way.

**A reviewer's free text stays with reviewers.** The reason of a decision is written by a person and can quote the exact arguments, so the operational disclosure treats it as a value. `approvals/{id}` returns `decision.reason_recorded` only. `evidence/{id}` of the signed decision record returns the record without `action_lifecycle.decision_reason` and lists it in `detail.withheld[] {field, why, read_with}`; `verification` is still the result of checking the signature over the **complete** stored record, so the returned `record` is, for that one field, not byte-equal to `talon audit show <id> --json` and does not reproduce the signature by itself. No other field of any record is withheld. The signed record is never modified; an approver reads the reason with `talon approvals show <approval-id>`. *(`TestApprovals_DecisionReasonStaysOnTheReviewerSurface`, `TestApprovals_NoArgumentValueOnAnyRouteAndNoMutation`, browser approvals journey.)*

**The lifecycle list is bounded and says so.** `lifecycle.records` holds at most 50 records, oldest first. When the operation has more, `lifecycle.truncated` is `true`, the list's availability is `partial`, and its note gives the command that verifies all of them. *(`TestApprovals_TruncatedLifecycleListSaysSo`.)*

**Findings.** `overview.findings` and a use case's `findings` carry `approvals_awaiting_decision` (severity `info`: a request waiting for a person is work to do, not a fault) for each use case with unresolved approvals not known to be undecidable, titled "N approvals await a decision" only when all of them are `actionable` and "may await a decision" otherwise, with the stored count and each inferred class in `why`; `approvals_unresolved` when the classes could not be established.

**Listing and paging.** `state=attention` (default) is unresolved approvals that are actionable, potentially actionable or unknown, oldest first; `unresolved` is every pending approval with its class; `decided` is history, newest first. Order and cursor are the approval's creation time and id, which never change: a page never repeats or skips an approval that stays in the selection, and an approval whose state changes between requests is reported with the state it has when its position is read and is absent from a selection it has left.

**Reads change nothing.** `action.Reader` issues `SELECT` statements only, on the console's `mode=ro` connection: no schema statement, no migration, no write, no lifecycle transition. A record is read in one transaction. Pinned by `TestReader_ReadOnlyConnectionAndNoMutation` and `TestApprovals_NoArgumentValueOnAnyRouteAndNoMutation` (every console route scanned for the fixture's argument values, write verbs refused, store state identical before and after), `TestApprovals_StoredCountsAndInferredEligibilityAreSeparate`, `TestApprovals_UnavailableIsNotZero`, `tests/browser/07-console-approvals.spec.js` (responses on the wire scanned for argument values; no decision control on any page) and the real-process operator journey in `TestE2E_ActionGateway_ArgumentRules`.

### 2.6 Operational readiness (#533)

`overview.readiness` and `system.readiness` answer whether the installation can serve governed traffic now, from the sources that can say so. `Scope` is always `installation`: no tenant scope filters it, so a tenant view never hides a shared outage. It is kept apart from canonical fleet health (`fleet.Evaluate`, unchanged), which judges use cases from budgets, policy and recorded traffic; neither is folded into the other, and the fleet `health` field is not redefined.

| Dimension | `ok` | `degraded` | `unverified` / `unknown` | `not_configured` |
|---|---|---|---|---|
| `runtime.gateway`, `runtime.mcp_proxy` | the role runs (§2.4) | stale; or expected and offline (including "failed to start") | unknown: records unreadable, or the role's config cannot be parsed | not expected and not reported; a stopped earlier instance of an unexpected role is history |
| `configuration.activation` | every running proxy and gateway loaded the config file the console reads now (`runtimestatus.ProveProxy`, `ProveGatewayConfig`) | a running process loaded a different version, or rejected a reload and serves its previous generation | unverified: a process did not report the digest; unknown: no running process of an expected role | no gateway or proxy configured |
| `authentication.agent_keys` | every running gateway and proxy reports holding the key of every use case that declares one | an expected role failed to start with `agent_key_unavailable`, or a running process does not hold a declared key | unverified: a running process does not report `agent_keys` (a fresh heartbeat proves nothing about authentication); unknown: no running process | no use case in the running generation declares a key (requests are attributed, not authenticated by key) |
| `data.evidence_store`, `data.session_store` | readable now (record count and newest record for evidence; a recent record shows something wrote, not that a process runs) | cannot be read | — | — |
| `data.runtime_records` | records of this installation read | records rejected: another evidence signing key fingerprint, malformed or unsupported | unknown: the console has no data directory or signing key | — |

`overall`: `degraded` when any dimension is degraded; otherwise `not_configured` when neither runtime is configured; otherwise `unknown`, then `unverified`, then `operational`. Each dimension states its `source` and `observed_at` (when the underlying state was established; absent when nothing established it). The console never attempts authentication and holds no key: `agent_keys` is each process's own report. Recorded traffic is not used: zero requests are neither healthy nor unhealthy, and a recorded policy denial is evidence, not an operational finding.

`findings[]` carry `severity` (critical, warning, info), `code`, `scope` (`installation` or `use_case`), `title`, `affected`, `why`, `source`, `observed_at` and `link` (a console route to continue from). Installation codes: `runtime_offline`, `runtime_failed_to_start`, `runtime_stale`, `runtime_unknown`, `config_not_active`, `reload_rejected`, `agent_keys_unavailable`, `agent_keys_unverified`, `data.evidence_store_unavailable`, `data.session_store_unavailable`, `runtime_records_unavailable`, `runtime_records_unknown`, `runtime_records_rejected`, `runtime_records_foreign_key`. `overview.findings` adds one `fleet_<health>` finding per not-healthy fleet row of the tenant scope, with fleet's own `why` (blocked is critical, needs-attention a warning, a disabled use case info). Order: severity, installation before use case, code, affected. Pinned by `TestReadiness_*` (the 15 PR scenarios), `TestUseCaseFindings_KeepCanonicalHealth`, `TestE2E_ConsoleReadiness_UndecryptableAgentKey` (the People Analytics failure over real processes: with `TALON_ADMIN_KEY` unset, both `serve --gateway` and `serve --proxy-config` refuse to start on an undecryptable key and nothing reaches the HR backend, the console reads degraded in every tenant scope, and a control run with the original secrets key authenticates the right key and refuses a wrong one) and `tests/browser/05-console-readiness.spec.js`.

### 2.5 Effective policy (#305)

`effective.Build` reports these layers, which are never merged into one claim:

1. **Current files**: the agent file (canonical policy digest: comments and formatting are not policy), the gateway config and the MCP proxy config, each with its sha256 or why it is unusable.
2. **Loaded**: `runtimestatus.ProveLoaded` compares the current file's policy digest with what the current *running* processes report (§2.4): `loaded_matches_file`, `loaded_differs_from_file`, `not_in_active_generation`, or `unknown` (records unreadable, no running process reports a catalog, processes disagree, or a digest is missing). A stale or history instance proves nothing.
3. **Effective**: `gateway.ExplainEffectivePolicy` calls `ResolveEffectivePolicy`, the function the gateway enforces with, and explains caps (daily, monthly, session: use case replaces the organization default when > 0, the organization ceiling binds too, tightest positive wins), `pii_action` (organization floor, use case only tightens), `forbidden_tools` (union of organization, provider and use-case lists), `tool_policy_action` (provider over organization default, use case only tightens) and `allowed_models` (use-case list plus organization and provider hard constraints). Every rule's effective value is the resolver's; `TestExplainEffectivePolicy` pins that the explanation never disagrees with it. `providers[].effective_digest` is the digest the gateway signs into evidence as `policy_digests.effective` for that provider. Proof is per enforcement boundary (`runtimestatus.ProveGateway`, `ProveProxy`): `effective.proven_active` is true only when every running **gateway** reports the current agent file's policy digest *and* loaded the current gateway config (sha256 of the bytes it read at start); otherwise `effective.proof` says why (`no_running_process`, `loaded_differs_from_files`, `unknown`) and `basis` says the values are compiled from the current files. A running MCP proxy proves nothing about the gateway policy, and a gateway config edited without a restart is never called active.
4. **MCP boundary**: for each tool the proxy config or the agent names, `mcp.EvaluateToolAccess` runs the proxy's own pre-dispatch checks (`forbidden_tools` match, then the proxy policy) and says where a denial happens. A config that cannot be loaded yields an error and no decisions. `mcp_boundary.proven_active` is proved on its own: every running **MCP proxy** loaded the current proxy config.
5. **Action boundary** (`action_boundary`, #425/#205): `action.CompileEffectiveActionPolicy` composes the company action policy of the gateway config with the use case's own, the function `talon serve` compiles at start. `actions[]` lists the actions the agent file defines with `verdict`, `verdict_source`, `decision_basis` and the rules that apply; `approval_rules[]` and `argument_rules[]` list every rule of both layers with `source` (`company` | `use_case`), `actions`, `condition`, `type`, `effect` and `approver_groups`. `decision_basis: arguments` means `verdict` is only the baseline: a call's arguments can make it stricter, never looser, and the console labels it "Depends on arguments", not "Allowed". Actions discovered from MCP sources are not listed (the report runs no discovery). An unreadable gateway config or a policy that does not compile yields `error` and no rules. `proven_active` has its own proof (`proof`, `runtimestatus.ProveActionPolicy`), not the LLM gateway's: the Action Gateway is served by every `talon serve`, so every running serve process must report this agent file in its active generation **and** the digest of the gateway config it read the company action policy from at start. A serve started without `--gateway` reads the company action policy from the file but does not report its digest, so the action policy then reads *not proven active* (unknown), never proven. An action with no rule reads "Allowed by policy". The evidence detail page shows the decision an `action_lifecycle` record carries (`verdict`, `matched_rule_id`, `matched_rule_source`, approval state); a record never carries the call's argument values.
6. **Last decision**: the newest record of a **request decision at an interception boundary** (the newest observation of layer 7; whether that record establishes the use case's own credential is layer 7's `identity_proven`), re-read through the verifying path (`evidence.Store.Detail`, `verification: valid|invalid`); a record whose signature fails is still pointed at but reads `unverified` for both digest comparisons and is never presented as authenticated. Otherwise: its decision and dispatch outcome, and whether its recorded agent and effective digests equal the current ones (`same` / `different` / `not_recorded`; `matches_current:<provider>` / `differs_from_current` / `not_recorded`). MCP proxy records carry no policy digests and read `not_recorded`, never assumed equal. Operator and configuration events (a registration, enable/disable, a reload, a budget threshold) are not decisions and are never selected (#472).
7. **Connection and verification** (`verification`, #472): independent observations, not a lifecycle. `configured` (`enabled` | `disabled`, from the agent file). `credential` is what is known about the credential the use case presents now: `state` (`known`; `absent`: the vault was read and holds no key under the name the agent file binds; `no_key`: the agent file binds none; `not_recorded`: a key is stored, but the vault holds no record of when its value was written, because the vault predates value versions; `unknown`: the vault could not be read, or no vault file is visible to the reading process, which is not taken to mean that the key is gone), `secret_name`, `since` (an upper bound of when the stored value was written, at most a millisecond after it), `generation` (values written under the secret name since the vault records versions), `history` (`only_value`: no other value has ever existed under the name; `only_value_since_record`: none since the vault began to record versions, earlier ones unknown; `earlier_values`; `not_recorded`), `registration` (the newest signed `agent_registered` record with its signature check; absent for a use case configured by hand), and `runtime` with `runtime_note`: `holds_current` (no running process can hold another value), `predates_current` (a running process built its generation before `since`), `not_established` (a running process was already running at `since` and has rebuilt its generation since: a rebuild keeps the previous key when the vault read fails, and no record says which happened), `not_running`, `unknown`. These facts come from the vault's **version record** (`secret_value_versions`), read through a read-only connection with no decryption key: it is maintained by triggers on the secrets table, so it commits with every write of a value, and a re-encryption (`talon secrets rotate`) is not a new version. The vault's access log is not used. `traffic[]`, one entry per boundary in a fixed order (`llm_gateway`, `mcp_proxy`, `action_gateway`), each `state: observed | none | unavailable` with `establishes` (what an observation there does and does not prove) and, when observed, `evidence_id`, `timestamp`, `invocation_type`, `event` (Action Gateway), `identity` (how the request was tied to the use case) and `identity_proven` (true at the LLM gateway and the Action Gateway, where a record under a use case exists only when its Talon key or a verified workload identity was presented; false for MCP proxy records, which do not record how the caller was identified: the proxy uses the presented agent key when there is one and its own configured agent name on admin-key or development-open requests; false for records of the no-key quickstart profile, which carry the `quickstart_mode` annotation; false for any record whose signature fails), `credential` with `credential_note` (which credential the request was authenticated with, as far as recorded times establish it; evidence does not record the credential a request presented: `current` only when the runtime records say which processes can have served the record (processes with the boundary's role whose record covers the moment; a process that stopped reporting without a stop record counts for as long as the assessment waits before calling it offline; records are kept for seven days), at least one can, and none can hold another value: each started after `since`, or the value is the only one in this vault file since it began to record versions (for a new vault: since the file was created) and each started after that. No history is a shortcut: `only_value` is a fact about the vault file. `previous` when the record predates `since`, or when the vault holds no key for the use case any more; `not_established` when it is newer than `since` and a process that can have served it had started before that floor, or the runtime records do not cover the moment and another value existed before; `unknown` also when the runtime records do not cover the moment and no other value is recorded, and for an LLM gateway record made under another version of the agent file (which secret the use case was bound to then is not recorded); `unknown` when the vault facts cannot be read or the vault holds no version record for the value; `not_applicable` for a verified workload identity), `session_id`, `outcome` (decision, dispatch, downstream), `verification` (signature) and `policy`: `matches_current` (every recorded digest equals what the current files compile to), `differs_from_current`, `not_recorded` (no digest, or only part of them: a partial match is not a match), `unverified` (signature invalid: nothing is compared) or `bound_at_establishment` (an Action Gateway record that is not the establishment: it carries the policy bound to the operation when it was established, which is not a policy evaluated for this event), with `policy_note`. For the Action Gateway the observation is the newest record of an explicit list of lifecycle events that only an **application request** causes: `operation_established`, `operation_conflict`, `attempt_claimed`. `authorization_refused` (also written for a reviewer without authority), `approval_requested`, `approval_decided`, `attempt_armed` and expiry never count, and `attempt_completed` is reported separately as `last_dispatch`: establishing or claiming an action is not dispatching it. Each of these events is read with its own indexed lookup (`evidence.Store.NewestActionEvent`, expression index `idx_evidence_action_event`), so a qualifying record is found however many reviewer or system events were recorded after it; there is no window of newest records. Qualifying records are an explicit list of invocation types per boundary, not "every request-class record": registration and other operator events, provider sub-attempts, imported external events and native runs establish nothing here, and a request with an unknown key is rejected before any record is written. `reading {code, text}` is a one-line presentation summary derived in Go (`registered_not_loaded`, `registered_activation_unknown`, `loaded_no_traffic_observed`, `traffic_observed_policy_matches`, `traffic_observed_policy_differs`, `traffic_observed_policy_not_proven`, `traffic_observed_identity_not_established`, `traffic_predates_current_credential`, `traffic_observed_current_credential_not_established`, `traffic_record_unverified`, `evidence_unavailable`, `disabled`). A newest record that fails verification is stated first; otherwise the reading speaks about the newest record with `identity_proven`, and says "traffic attributed … observed, but an authenticated connection is not established" when no record establishes the use case's own credential (only MCP proxy or quickstart records exist). Among authenticated records the reading prefers one attributed to the current credential: `traffic_predates_current_credential` when every authenticated record predates it (history of an earlier registration or a replaced key: never "verified"), `traffic_observed_current_credential_not_established` when a newer record exists but does not establish it. The time of a record alone never verifies the current credential. It is not a stored state, and the browser derives nothing. `not_established[]` lists what the observations do not prove (first: that all of the application's requests go through Talon). `serving {role, state, reason}` is the loaded proof restricted to the processes that serve the use case's requests: `role` is `gateway` when its newest authenticated request arrived at the LLM gateway (or none arrived yet and the gateway config enables a provider), absent when any Talon process serves them. `next {code, text, commands[]}` is the one thing to do next, or that nothing needs doing: a fixed mapping from the facts above to a sentence and, where one exists, complete Talon commands (`none`, `enable`, `start_runtime`, `check_runtime`, `fix_reload`, `wait_reload`, `send_request`, `send_new_request`, `check_policy`, `restart_runtime`, `use_current_key`, `store_key`, `verify_evidence`, `check_evidence`, `use_authenticated_boundary`). `none` needs the newest authenticated record to verify under the current policy, a running process of the serving role that has loaded the use case (`serving`), and credential facts that do not contradict it: not while a running process holds an earlier key or is not established to hold the stored one, and not for a record that does not say which secret authenticated it. When the credential is not known at all (no version record, no visible vault) the text of `none` says that it does not rest on which key the request used. The reading follows the newest authenticated record over all boundaries. The console prints it in the Summary and under the reading; the commands are text to run in a terminal, the console runs nothing. Each lookup is one indexed range read per invocation type (`evidence.Store.NewestByType`, index `idx_evidence_tenant_agent_type_ts`) or per action event (above). The console shows `reading` in the use case's Summary and the credential facts and the full table under Policy & Runtime. Pinned by `TestVerification_*`, `TestNextStep_IsDeterminedByTheFacts`, `TestValueVersions_*` (the vault), `TestComparePolicy_ActionBoundVersusEvaluated`, `TestCredentialFacts_ReadTheVaultReadOnly`, `TestE2E_Onboarding_FirstAndSecondApplication` (CLI = console), `TestE2E_Onboarding_CredentialLifecycle` (history, not established, current, with real processes) and `tests/browser/08-console-verification.spec.js`.

The report is read-only: files, runtime records and the store. It is not a dry run of a request (no model, prompt or PII content is evaluated) and does not cover OPA rules beyond what the proxy policy decides for a bare tool name.
